# Prompting and schema design for Video Import (gemini-2.5-flash-lite via OpenRouter)

Fetched 2026-10-01. Sources are primary docs only. Claims not found in a primary source are marked UNVERIFIED.
Source URLs fetched as raw markdown: `https://ai.google.dev/gemini-api/docs/{structured-output,prompting-strategies,thinking}.md.txt`, OpenAI `https://developers.openai.com/api/docs/guides/structured-outputs`, OpenRouter `https://openrouter.ai/docs/guides/features/structured-outputs.md` and `.../plugins/response-healing.md`, `https://openrouter.ai/api/v1/models`.

## Summary: ranked recommendations

1. **Make "no recipe" a first-class, schema-visible answer.** The model "will always try to adhere to the provided schema" and then hallucinates (OpenAI). An empty `recipes` array is the only way out today, and it is easy to miss. Add a required `hasRecipe` boolean (or `verdict` enum `"recipe"|"none"`) before `recipes`, and a short required `reason`. Server side: if `hasRecipe=false` return `NoRecipe`, and ignore `recipes`.
2. **Make `ingredientLines` and `steps` non-nullable, `minItems: 1`, and `title` non-null.** Nullable fields are an explicit invitation to emit stubs. A stub can then no longer be produced without inventing content, and the model has the escape hatch from #1 instead. Keep `servings`/minutes nullable. In C#, change `IReadOnlyList<string>?` to non-nullable and add a schema transform for `minItems`. Check that OpenRouter/Google actually enforces `minItems` (Google lists it as supported). Keep the server-side `Validate` as a backstop.
3. **Add the empty case to the prompt as a literal few-shot, in the same format as the real examples.** Google: "always include few-shot examples". OpenAI: "include language in your prompt to specify that you want to return empty parameters". Keep the existing positive example. Add a second input/output pair: a chapter list plus `[Music]` transcript mapped to `{"hasRecipe": false, "reason": "...", "recipes": []}`. Keep the formats consistent across examples.
4. **Move the schema description of each field into `description` (Google: "Clear descriptions: Use the `description` field to guide the model"), e.g. "Only fill from transcript; one string per step, not an object".** Do not rely on prose alone for shape. The bare `[]` and `{"text":..}` drift is a schema-enforcement symptom; see the OpenRouter caveat in finding 1.
5. **Verify enforcement is real on the routed endpoint.** Send `provider: {require_parameters: true}` and `strict: true`. OpenRouter: "Enforcement varies by provider ... exact compliance is not guaranteed on every endpoint". The `[]` / `{"text"}` drift suggests the schema may be treated as a hint on the current route. Check the response's provider in the logs.
6. **Put the transcript first and the task/question last in the user message** ("Based on the information above..."). Keep the role, output format and rules in the system prompt. This matches Google's long-context guidance; see finding 3.
7. **Cheap model upgrade as a fallback or A/B.** `google/gemini-2.5-flash` is $0.30/$2.50 per M, about 3x the input and 6x the output price of flash-lite ($0.10/$0.40). `openai/gpt-4.1-mini` costs $0.40/$1.60 and `openai/gpt-5-mini` $0.25/$2.00. All list `structured_outputs`. Whether flash-lite is "adequate" has no primary-source statement; run the golden set against 2.5-flash. Typical import cost stays tiny.
8. **Optional: a `reasoning`/`evidence` field before `recipes`.** Evidence (e.g. a transcript quote per recipe) is UNVERIFIED as a Gemini-recommended technique. See finding 3. Try it only if #1 to #3 are not enough.
9. **Retry once on `LlmBadOutput`/`NoRecipe-with-stubs` with the validation error appended.** No provider doc recommends this explicitly; see finding 4. Weigh the cost.
10. **Temperature 0.2 stays.** The only primary guidance on temperature is Gemini 3.x ("keep default"). For 2.5 it is UNVERIFIED either way; see finding 1.

## 1. Gemini structured output

- **Supported subset.** "Gemini's structured output mode supports a subset of the JSON Schema specification." Types: string, number, integer, boolean, object, array, null. `object`: `properties`, `required`, `additionalProperties`. `string`: `enum`, `format`. Numbers: `enum`, `minimum`, `maximum`. Arrays: `items`, `prefixItems`, `minItems`, `maxItems`. `anyOf` appears in the content-moderation example. Source: https://ai.google.dev/gemini-api/docs/structured-output.md.txt (section "JSON schema support").
- **Nullable.** "To allow a property to be null, include `"null"` in the type array (e.g., `{"type": ["string", "null"]}`)." Same page. So nullability is opt-in. In our case the C# `?` produces exactly this, which permits null stubs.
- **`required`.** "`required`: An array of strings, listing which properties are mandatory." Same page. The doc says nothing about optional fields being omitted vs. null. UNVERIFIED for Gemini. OpenAI does say the following: "Although all fields must be required (and the model will return a value for each parameter), it is possible to emulate an optional parameter by using a union type with null." https://developers.openai.com/api/docs/guides/structured-outputs
- **Descriptions.** "`title`: A short description of a property. `description`: A longer and more detailed description of a property." under "These descriptive properties help guide the model". Best practices: "Clear descriptions: Use the `description` field to guide the model." / "Strong typing: Use specific types (`integer`, `string`, `enum`)." / "Prompt engineering: Clearly state what you want the model to do." / "Validation: While output is syntactically correct JSON, always validate values in your application." / "Error handling: Implement robust error handling for schema-compliant but semantically incorrect outputs."
- **Constraints.** `minItems`, `maxItems`, `enum`, `minimum`/`maximum` are listed as supported. The doc does not say whether they are enforced by constrained decoding or only hinted. UNVERIFIED. `minLength` is not in the supported list for strings (only `enum` and `format`).
- **propertyOrdering.** The current structured-output page does not mention it (grep found no mention). Importance is UNVERIFIED from the sources I fetched. Practical use: if an escape-hatch/reasoning field is added, place it first in the schema and the C# record order (System.Text.Json generates schema in declaration order).
- **Limits.** "Not all JSON Schema features are supported." / "Very large or deeply nested schemas may be rejected."
- **Prompt vs schema duplication.** The doc says only "Prompt engineering: Clearly state what you want the model to do". There is no explicit "don't duplicate the schema in the prompt" rule. UNVERIFIED. OpenAI says "No need for strongly worded prompts to achieve consistent formatting" (structured outputs on). OpenRouter: "Include descriptions: Add clear descriptions to your schema properties to guide the model", and "Use strict mode: Set `strict: true`... Enforcement varies by provider: some guarantee schema-conforming output, while others ... treat it as a strong hint, so exact compliance is not guaranteed on every endpoint". https://openrouter.ai/docs/guides/features/structured-outputs.md . Implication: the prompt should keep one short example of the shape because OpenRouter does not guarantee enforcement.
- **Routing.** "Support is determined per endpoint, not just per model"; use `require_parameters: true` with `response_format.type: json_schema`. Same OpenRouter page (also on https://openrouter.ai/docs/features/structured-outputs).
- **Response healing.** The plugin "automatically validates and repairs malformed JSON responses ... missing brackets, trailing commas, markdown wrappers, or mixed text"; "activates for non-streaming requests". https://openrouter.ai/docs/guides/features/plugins/response-healing.md . It repairs syntax only. It will not fix `[]` vs `{"recipes":[]}` or object-vs-string items (UNVERIFIED for schema-level fixes; the doc lists syntax cases only).
- **Temperature.** Gemini docs: "we strongly recommend keeping them at their default values for Gemini 3.x models. Changing these parameters (for example, setting the temperature below 1.0) can cause unexpected behavior, such as looping or degraded performance". https://ai.google.dev/gemini-api/docs/prompting-strategies.md.txt . This is explicitly for 3.x. There is no 2.5 statement in the fetched pages, so 0.2 vs 1.0 for 2.5-flash-lite is UNVERIFIED. The generic text: "Lower temperatures are good for prompts that require a more deterministic or less open-ended response".
- **Thinking.** Table in https://ai.google.dev/gemini-api/docs/thinking.md.txt : `gemini-2.5-flash-lite | Off | low, medium, high` and `gemini-2.5-flash | On | low, medium, high`. So flash-lite does not think by default, while 2.5-flash does. On OpenRouter use the `reasoning` parameter (`effort`/`max_tokens`, https://openrouter.ai/docs/guides/best-practices/reasoning-tokens.md); "Reasoning tokens are considered output tokens and charged accordingly". The effect on schema compliance is UNVERIFIED in the docs. Enabling low reasoning on flash-lite is an experiment option.

## 2. Schema design for the "no recipe" case

- **What the docs say about forced-schema hallucination.** OpenAI: "The model will always try to adhere to the provided schema, which can result in hallucinations if the input is completely unrelated to the schema. You could include language in your prompt to specify that you want to return empty parameters, or a specific sentence, if the model detects that the input is incompatible with the task." https://developers.openai.com/api/docs/guides/structured-outputs ("Handling user-generated input"). This matches our observed behaviour (10 stub recipes from a chapter list).
- **Nullable fields invite null output.** No primary doc states this causally. UNVERIFIED as a documented phenomenon; it is a mechanical consequence of the schema permitting null (Google: `["string","null"]` makes null valid) and of the model being pushed to emit something per array item.
- **Constraints.** `minItems` is supported (Google). Using `minItems: 1` on `ingredientLines`/`steps` and making them non-null removes the stub shape from the valid output space (if enforced; check by test). The escape hatch must then be available: `hasRecipe: false` with `recipes: []` (no `minItems` on `recipes` itself).
- **Discriminator pattern in Google's own example.** The content-moderation example uses `anyOf` with `enum` and per-branch required fields: a decision object with different shapes (spam details vs not-spam details). A union `{status: "none", reason}` | `{status: "recipes", recipes: [...]}` is the documented style. Whether flash-lite via OpenRouter handles `anyOf` reliably is UNVERIFIED; a flat `hasRecipe` bool is safer.
- **Evidence quotes.** No primary source recommends quote-evidence fields for hallucination reduction. UNVERIFIED. Possible cheap form: `evidence: string[]` per recipe, required `minItems: 1`, validated server-side as a substring of the transcript (our own check, not provider guidance).
- **Server-side backstop (already present).** `Validate` drops entries without ingredients/steps. Note a mixed case: all-stub replies end as `LlmBadOutput`, not `NoRecipe`. With `hasRecipe` the correct failure kind becomes reachable. Treat "all entries invalid" as `NoRecipe` if `hasRecipe=false` or the golden set expects it (design decision for the caller).

## 3. Prompting techniques

- **Few-shot.** "We recommend to always include few-shot examples in your prompts. Prompts without few-shot examples are likely to be less effective. In fact, you can remove instructions from your prompt if your examples are clear enough in showing the task at hand." Also: "if you include too many examples, the model may start to overfit" and "it is essential to ensure a consistent format across all examples". https://ai.google.dev/gemini-api/docs/prompting-strategies.md.txt . No explicit "negative/empty example" advice from Google. The OpenAI "return empty parameters" wording above is the nearest primary support. Current prompt has only one illustrative example (shape only) and a prose rule; a literal empty example is the missing piece.
- **State the empty case literally.** Already done in prose ("antworte mit `{"recipes": []}`"). OpenAI advice (above) suggests the same, in the prompt. Keep, but align with the new field (`hasRecipe: false`).
- **Placement.** "Prioritize critical instructions: Place essential behavioral constraints, role definitions (persona), and output format requirements in the System Instruction or at the very beginning of the user prompt." and "Structure for long contexts: When providing large amounts of context (e.g., documents, code), supply all the context first. Place your specific instructions or questions at the very *end* of the prompt." and "Anchor context: After a large block of data, use a clear transition phrase ... 'Based on the information above...'". Both under "Gemini 3" practices, so applicability to 2.5 flash-lite is UNVERIFIED. Current layout: system prompt has everything; user message is Title/Description/Transcript with no trailing instruction. Adding a short closing line ("Basierend auf dem Text oben: gibt es ein Rezept? Antworte nur im Schema; keine Zutaten und Schritte im Text → keine Rezepte.") follows the guidance.
- **Structure.** "Use consistent structure: ... XML-style tags (e.g., `<context>`, `<task>`) or Markdown headings are effective. Choose one format". Wrapping the transcript in tags would follow this.
- **"Think then answer" field.** OpenAI structured-outputs guide has a "Chain of thought" example ("You can ask the model to output an answer in a structured, step-by-step way"), implemented with a steps array in the schema. For Gemini there is no primary statement. Google thinking page covers native thinking only. UNVERIFIED for Gemini structured output; an explicit `reason` field before `recipes` is a low-cost analog.
- **Model size.** No primary doc says flash-lite is inadequate for extraction. Google's thinking guidance: "minimal or low thinking for fact retrieval" vs "maximum thinking for advanced coding, math, or multi-step planning" (paraphrased from the thinking page). Our task is extraction plus a negative-judgement call. Treat adequacy as an empirical question for the golden set.

## 4. Retry / validation-loop patterns (only what docs say)

- Google: "always validate values in your application" and "Implement robust error handling for schema-compliant but semantically incorrect outputs." No explicit re-ask loop in the fetched pages.
- OpenAI: "Structured Outputs can still contain mistakes. If you see mistakes, try adjusting your instructions, providing examples in the system instructions, or splitting tasks into simpler subtasks." The same guide lists "No need to validate or retry incorrectly formatted responses" as a benefit for strict schemas. It says nothing about re-asking with the error.
- OpenRouter: Response Healing repairs syntax (non-streaming). No retry-with-error pattern in the fetched pages.
- Conclusion: a re-ask with the validation error is not recommended by the primary docs I read (Anthropic not checked). Treat it as our own design choice. "Splitting tasks into simpler subtasks" (OpenAI) is documented, e.g. step 1: "does the text contain any recipe? yes/no" (tiny schema), step 2: extraction only when yes. This is the strongest documented route if the single-call fixes do not hold.
